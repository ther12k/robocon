## Summary

Desktop fidelity alone does not make this workspace usable on narrow screens. Responsive changes must not create new controllers or sticky input.

## Source grounding

Planning baseline: `f5092ffa5aa8eeb9aaab016dfa4b8a303c14c12a`. [S03](https://github.com/ther12k/robocon/blob/f5092ffa5aa8eeb9aaab016dfa4b8a303c14c12a/src/style.css#L1-L36) [S22](https://www.w3.org/TR/WCAG22/) [S23](https://www.w3.org/TR/pointerevents3/)

This issue describes proposed work. Re-check the implementation checkout before treating a gap as current; do not reintroduce or duplicate already-landed audit fixes.

## Integration points

- New: src/ui/styles/responsive.css
- Existing integration: ArenaViewport and PanelManager

## Implementation tasks

- [ ] Implement the four breakpoint arrangements and arena-first phone ordering.
- [ ] Make inspector/editor drawers accessible with virtual keyboard and orientation changes.
- [ ] Keep the drive pad in a dedicated touch region and allow ordinary page scrolling elsewhere.
- [ ] Ensure reflow does not remount the engine/canvas, lose drafts or change transport ownership.

## Acceptance criteria

- [ ] No horizontal page overflow at 360, 390, 768, 1024 and 1440 px widths.
- [ ] 44 px drive targets and Stop remain reachable; no fixed footer overlays them.
- [ ] Orientation change during pointer hold releases input safely and retains world state.

## Test evidence required

- [ ] Browser viewport matrix including 390×844 and 360×800; touch emulation and rotation.
- [ ] Manual real-device check recorded separately; do not claim mobile support from desktop emulation alone.
- [ ] Attach actual source SHA, command/output or review artifact, and any blocked checks. Do not claim execution from source inspection.

## Boundaries and completion

Preserve authoritative simulation, match, replay and Worker contracts. Views do not manipulate physics directly. New manual interactions must use the approved input/command path. Do not add unsupported battery, weather, lift, account or official-arena claims to match the illustration.

A completed PR names this planning ID and its real GitHub issue number, records any intentional deviation, and links its evidence. Numeric IDs are assigned only when issues are actually registered.
