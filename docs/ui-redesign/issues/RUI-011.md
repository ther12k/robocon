## Summary

The new pad cannot be a second input pipeline. A single arbiter must prevent manual samples from fighting Worker or replay control.

## Integration points

- Existing: src/sim/input/InputManager.ts, src/main.ts input loop
- New: src/app/InputArbiter.ts, src/ui/components/DrivePad.ts

## Implementation tasks

- [ ] Define focused keyboard and pointer states and the documented forward/turn/strafe mapping.
- [ ] Normalize differential-drive lateral input to unavailable; retain holonomic strafe controls.
- [ ] Use pointer capture and clear state on up/cancel/lost capture/blur/visibility/panel/source/slot change.
- [ ] Scope Tab and character shortcuts to a deliberate driving context; never intercept native slider/form keys.
- [ ] Submit only the current authoritative source for each slot through existing command ingress.

## Acceptance criteria

- [ ] Holding and releasing any supported input produces the expected command and subsequent neutral state.
- [ ] No manual zero command overwrites a running autonomy source.
- [ ] Pointer controls never orbit the arena or trigger measurement.
- [ ] A lost release event cannot leave movement latched.

## Test evidence required

- [ ] New tests/inputArbiter.test.ts covers simultaneous keys/pointers and source transitions.
- [ ] Browser: mouse, touch emulation, cancel, blur, modal open and slot switch; inspect delivered commands.
- [ ] Attach actual source SHA, command/output or review artifact, and any blocked checks. Do not claim execution from source inspection.

## Boundaries and completion

Preserve authoritative simulation, match, replay and Worker contracts. Views do not manipulate physics directly. New manual interactions must use the approved input/command path. Do not add unsupported battery, weather, lift, account or official-arena claims to match the illustration.
