# [RUI-039] Design and implement richer replay transport only as a separate increment

**Issue ID:** `RUI-039`
**Scope:** `deferred`
**Priority:** `P3`
**Milestone:** `M5 - Deferred capabilities`
**Estimate:** `L` — relative effort, not a calendar commitment
**Labels:** `project:robocon-light-ui`, `type:feature`, `area:replay`, `priority:p3`, `scope:deferred`

## Summary

Pause, seeking and playback-rate controls are not launch capabilities. A draggable timeline would otherwise promise behavior the engine has not proved.

Planning baseline: `f5092ffa5aa8eeb9aaab016dfa4b8a303c14c12a`. [S09](https://github.com/ther12k/robocon/blob/f5092ffa5aa8eeb9aaab016dfa4b8a303c14c12a/src/core/SimulationCore.ts) [S17](https://github.com/ther12k/robocon/blob/f5092ffa5aa8eeb9aaab016dfa4b8a303c14c12a/src/core/replayFile.ts)

This issue describes proposed work. Re-check the implementation checkout before treating a gap as current; do not reintroduce or duplicate already-landed audit fixes.

## Integration points

- Future: replay transport/domain scheduler and versioned tests

## Implementation tasks

- [ ] Specify pause/seek/rate semantics and compatibility with match logs/checkpoints.
- [ ] Prototype reset-and-fast-forward versus true state snapshots; document cost and state completeness.
- [ ] Bound replay seeking work and make cancellation/session switching safe.
- [ ] Add controls only after final-state, checkpoint and seek-equivalence tests pass.

## Acceptance criteria

- [ ] No decorative seek/rate control is enabled before implementation.
- [ ] Seeking to a tick produces the same authoritative state as sequential playback.
- [ ] Chosen method documents memory/CPU limits and schema/version consequences.

## Test evidence required

- [ ] Future randomized seek-versus-sequential fixtures including scoring/retry/grip.
- [ ] Future browser long-replay cancellation and bounded-time performance tests.
- [ ] Attach actual source SHA, command/output or review artifact, and any blocked checks. Do not claim execution from source inspection.

## Boundaries and completion

This is **not a dependency of the light-dashboard launch**. Keep its related affordance omitted or explicitly unavailable until an independently approved implementation and evidence exist. Feasibility/design findings are not implementation completion.

A completed PR names this planning ID and its real GitHub issue number, records any intentional deviation, and links its evidence. Numeric IDs are assigned only when issues are actually registered.
